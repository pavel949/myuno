# Технический аудит myUNO

**Дата снимка:** 2026-03-23  
**Область:** архитектура, качество кода, безопасность, CI/CD, тесты, бэкенд, технический долг  
**Источники:** `src/`, `supabase/`, `.github/workflows/`, `package.json`, документация в `docs/`

---

## 1. Краткое резюме

| Вопрос | Ответ |
|--------|--------|
| **Зрелость инженерной базы** | Средняя+: **CI** (lint → typecheck → unit tests → production build), **Vite** + **React Query**, **RLS** в Supabase, **Zod** для публичного env в prod. |
| **Главные риски** | **TypeScript `strict: false`**, низкое **автотестовое покрытие** относительно объёма кода, **большая поверхность** edge functions и миграций, **ESLint** по всему репо может давать много предупреждений/ошибок вне `src/`. |
| **Сильные стороны** | Чёткое разделение слоёв (hooks / components / pages), **APP_ROUTES**, единый Supabase client, **`dealAuditEncoding`** + порядок save/audit для CRM, **Playwright** согласован с Vite **порт 8080**. |

## 4. Качество кода (TypeScript, согласованность)

| Уровень | Находка | Рекомендация |
|--------|---------|--------------|
| **High** | `tsconfig.app.json`: **`strict: false`**, **`noImplicitAny: false`** | Поэтапно: `strictNullChecks` → `strict` по модулям |
| **Medium** | Много `any`, ESLint часто предупреждает на `no-explicit-any` | Включать stricter правила для новых директорий; типизировать публичные API хуков |
| **Low** | Централизованный **`logger`**, `no-console` инкрементально для части деревьев | Довести до единого стандарта в `src/`; SW/тесты — исключения |

**CRM / Sales (актуализация 2026-03):**  
- Единое кодирование аудита сделок: `src/lib/dealAuditEncoding.ts` (`auditFieldValue`), используется в `diffDealFields`, `useBulkUpdateStage`, UI.  
- Критичный путь: **сначала `update` в БД, затем `deal_field_changes`** (см. `docs/CRM-FIX-PLAN-2026-03.md`).  
- Список контактов: fallback запроса без embed при ошибке PostgREST (`useCrmContacts`).

## 5. Безопасность

| Уровень | Находка | Рекомендация |
|--------|---------|--------------|
| **Low** | Во frontend только **anon / publishable key**; привилегированная логика в Edge Functions | Не менять |
| **Medium** | CORS: при неизвестном Origin возможен fallback (см. `docs/CORS-POLICY.md`) | Ужесточить для чувствительных функций |
| **Low** | `dangerouslySetInnerHTML` в отдельных местах | Только доверенный контент; `sanitize` где нужно |
| **Medium** | RLS — в БД; полный аудит всех таблиц не зафиксирован в репо | Периодический SQL-аудит MC/CRM; паттерн `mc_can_access()` |

## 11. Приоритетные действия

1. **High:** ужесточение TypeScript поэтапно (`strictNullChecks` → `strict` по модулям).
2. **High:** расширение тестов — критичные потоки MC/CRM и оплаты.
3. **Medium:** единый стандарт логирования в `src/`; снизить ESLint noise в `supabase/functions` (отдельный config или фиксы).
4. **Medium:** CORS и регулярный аудит RLS для MC/CRM.
5. **Low:** централизация URL/констант; ADR для платежей и webhooks.
