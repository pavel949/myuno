# Tranche E0 — план устранения широкого доступа менеджеров (до E1)

Только документация и read-only проверка. Миграции, seed, изменения прав и рабочих данных не выполняются: назначения объектов и состав команд (Layantara / Кондоминиумы) пока не подтверждены.

## Что уже подтверждено (аудит 2E)
- `staff_can_access_property`: director/admin и manager/accountant получают доступ ко всем объектам компании; staff — только через активный `property_manager_assignments`; platform admin/uno_team — обход.
- Политики на бронирования (SELECT по активному членству), финансы объектов (ALL), ledger по счетам компании, CRM (смешанно: `mc_can_access` / прямая проверка роли; `crm_tasks` без проверки членства), properties (несколько разрешающих маршрутов, включая публичные одобренные листинги).
- Разрешающие политики PostgreSQL объединяются: новая политика пространства не сужает доступ, пока старые широкие политики действуют.
- Экспорт: `export-mc-data` (service role + фильтр в обработчике), `send-property-report` (проверка формы bearer-заголовка, объектная авторизация в обработчике не найдена; живое поведение не проверено).

## Шаг 1 — полный реестр обходов (read-only)
Каталожные SELECT-запросы к production, без вызова функций:
1. Все политики, ссылающиеся на `management_company_members`, `staff_can_access_property`, `mc_can_access`, `has_role`, `is_admin`-подобные функции.
2. Все SECURITY DEFINER функции, читающие/пишущие properties, bookings, orders, tasks, financials, ledger, CRM, с указанием grants (anon/authenticated).
3. Представления без `security_invoker`.
4. Edge-функции с service role и экспортом/отчётами/рассылками (поиск по `supabase/functions`).
5. Клиентские пути, обходящие RLS-ограничение через широкий resolver (`getAccessiblePropertyIds`, `useMyProperties`, промежуточные выборки `useAssignedProperties`).

Результат — таблица: объект · тип (политика/RPC/view/edge/клиент) · текущий предикат · кто получает доступ · статус (подтверждено / предположение) · целевое изменение.

## Шаг 2 — минимальные изменения (только проект)
- Один канонический предикат `can_access_property_in_scope(user, property, capability)`: платформенный админ → director/admin компании → член пространства, куда назначен объект → staff с активным назначением. Пока пространств нет, предикат эквивалентен текущему поведению.
- Заменить прямые проверки членства в перечисленных политиках на этот предикат (замена, а не добавление политик).
- RPC и view: перевести на тот же предикат или `security_invoker`; money-RPC остаются service_role-only.
- Edge-экспорт и отчёты: проверка JWT и объектного доступа через тот же предикат до service-role выборки.
- Клиентский resolver: использовать результат RLS, без собственного расширения доступа.

## Шаг 3 — разделение подготовки и включения
```text
E1a  схема пространств + предикат в режиме совместимости (поведение не меняется)
     -> условие: утверждённый дизайн
E1b  назначения объектов и членов команд (seed)
     -> условие: письменное подтверждение списков объектов и людей
E1c  включение ограничений: переключатель system_settings, замена политик
     -> условие: зелёная матрица изоляции на синтетических учётных записях
```
Откат каждого шага — отдельный исполняемый SQL в `docs/hardening/rollback/`; E1c откатывается выключением флага без изменения схемы.

## Шаг 4 — проверяемая матрица изоляции
Строки — роли: founder/platform admin; director; manager Layantara; manager Condo; manager с явным кросс-доступом; staff с назначением; staff без назначения; член другой компании; аноним.
Столбцы — ресурсы: properties, bookings/orders, Today, calendar, tasks (оба источника), financials, ledger, CRM contacts/tasks, owners, staff, export, report email.
Ячейка: ожидаемое allow/deny для SELECT и записи.
Дополнительно: переназначение объекта сбрасывает доступ и кэш; смена активной компании очищает пространство; режим «без пространств» совпадает с текущим поведением.
Исполнение: изолированный PostgreSQL harness с копией схемы и синтетическими пользователями; на production не запускается.
