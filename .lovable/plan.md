# Life OS: показываем на сайте ту же таксономию, что хранится в базе

## Что уже есть (проверено в базе)
В базе уже лежит готовая таксономия из четырёх уровней. Сайт показывает только первый уровень.

```text
Ситуация (34)  →  Сценарий (24)              →  Задача (82)                   →  Сервисы
leisure           leisure.celebration           venue, flowers, catering,        не связаны
                  «Свадьба и праздники»          event_planner
family            family.childcare               school, babysitter, tutor        не связаны
                  family.activities, family.pets
```
- Ситуации связаны с 1 330 конкретными сервисами напрямую, без задач (`catalog_life_map`). Из-за этого у «Туриста» 270 сервисов, а у 11 ситуаций — ни одного.
- Связи «задача → сервисы» нет: таблица `task_entity_map` упомянута в коде, но в базе её нет.
- Сценариев «День рождения», «Семейное торжество», «Дети: досуг и здоровье» пока нет. Их нужно добавить к существующим.

## Как будет устроено для клиента
1. **«Жизнь на острове»** показывает группы-ситуации из базы: Приезд, Жизнь, Отдых, Семья и дети, Праздники и события, Здоровье, Документы, Жильё, Бизнес. Роли («турист», «инвестор» и т.п.) остаются только фильтром «Я: …».
2. **Страница ситуации** показывает её сценарии из базы карточками («Свадьба и праздники», «Уход за детьми и обучение»…).
3. **Страница сценария** показывает список задач («Найти площадку», «Заказать цветы», «Нанять няню»). У каждой задачи — нужные сервисы и одна кнопка: «Забронировать», если бронь доступна, или «Отправить заявку».
4. Если у задачи пока нет сервисов, вместо пустого блока будет кнопка «Отправить заявку команде» с этой задачей в заявке.
5. Всё, что видно на сайте, читается из базы. Тексты, порядок и связи меняются в базе, а не в коде.

## Этапы
**Этап A — без изменения данных (делаю сразу):**
- Чтение сценариев и задач из базы и новые страницы: ситуация → сценарии → задачи → сервисы, адрес вида `/discover/:situation/:scenario`.
- Пока задачи не связаны с сервисами, сервисы для задачи подбираются по категории через уже существующие связи. Неизвестное остаётся пустым и не выдумывается.
- «Хлебные крошки», единый вид, RU/EN/TH, телефон и компьютер, тесты.

**Этап B — меняет рабочие данные (только после вашего отдельного «да»):**
- Новая таблица связей «задача → категория сервисов». Связь задаётся категорией, поэтому новый сервис в этой категории сам появляется в нужной задаче.
- Новые сценарии: «День рождения», «Семейное торжество», «Дети: досуг, здоровье, кружки». Существующие сценарии дополню новыми задачами.
- Ролевые и пустые ситуации скрою из списка, а не удалю. Старые адреса продолжат работать.
- Перед применением пришлю список всех сценариев, задач и привязок к категориям на проверку.

## Технические детали
- Чтение: `life_situations` → `life_scenarios` (life_situation_id) → `life_tasks` (life_scenario_id); сервисы — через существующий `useResolveLifeOSContext` / `catalog_life_map` с фильтром по категории.
- Новые хуки в `useLifeOS.ts`: `useLifeScenarios(situationId)` и `useLifeTasks(scenarioId)`. Новых клиентов не создаю.
- Новый маршрут `/discover/:code/:scenario` под существующим кластером; страницы в `components/navigation/v3`.
- Этап B: forward-only миграция `life_task_categories` (task_id, category_code, weight) с RLS «публичное чтение, запись только admin» и rollback в `docs/hardening/rollback/`; seed — отдельным шагом, с разрешения.
- Сначала проверю права на чтение `life_scenarios` / `life_tasks` для гостей. Если чтения нет, открыть его — тоже изменение базы, поэтому оно попадёт в этап B.
