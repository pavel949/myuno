# Existing property identity and off-plan reuse — source contract

No new physical project/unit registry or physical table is introduced. Existing UUIDs survive construction, resale, rental and management. This is a source audit; subsequent read-only Lovable inspection confirms the existing bridge and scoped RLS, while full actor/lifecycle behavior remains unverified.

| Entity / flow | Current source contract | Reuse decision |
|---|---|---|
| Developer | developers.id → property_projects.developer_id | Reuse; brand is not proof of a legal org/counterparty mapping |
| Project / complex | property_projects.id is canonical project; properties.project_id links unit | Reuse same project UUID. property_complexes and properties.complex_id are explicitly legacy/deprecated in 20260820010743 SQL; do not create a new complex row for off-plan |
| Physical rentable/sellable asset | properties.id, with unit_number, project_id and optional parent_property_id | Immutable physical UUID. Public/rental/owner/PMS projections refer back to it. Off-plan/resale/rental/management are relationships/offers, not new identities |
| Project sales inventory | project_units.id is sales catalogue row; project_units.property_id FK → properties.id is the SAME physical unit | Carry both identifiers explicitly. Never treat catalogue row UUID as a second physical UUID or synthesize a property ID from it |
| Existing bridge guards | 20260820014650: unique project+lower(trim(unit_code)); unique non-null property_id; FK to properties; backfill + sync_property_project_from_unit | Reuse stable code→existing catalogue row→existing property bridge. Unlinked/ambiguous rows need review. Do not rerun historical backfills or rely on unverified deployment |
| Building / parent asset | properties.parent_property_id FK and building_name exist; source search found no separate canonical building UUID table in generated types | Inspect actual parent/hotel/building use before extending. Do not convert building_name to an identity or assume parent_property_id is always a building. An optional building/phase extension can reference existing entities after review |
| Rental reservation | property_bookings.property_id → properties.id | Never replace property UUID when a unit becomes rentable; holds/bookings keep canonical references |
| Ownership / management | property_owners.property_id and property_management_terms.property_id; existing operating/property assignments | Reuse properties.id. Ownership and management status are independent from sale availability and construction |
| Legacy type inventory | development_units: floor ranges, total_units/available_units, names/types; deprecated by SQL | Template/aggregate evidence only; preserve and map, never use its row ID as a physical UUID or create fresh physical copies |
| Resale | resale_properties has its own row UUID and development_id; no proven physical property bridge | Real unresolved mapping gap. Match reviewed aliases to existing properties.id before import; a resale listing row is not a new asset |
| Domain view | v_real_estate_domain_chain UNION ALL emits properties/project_units/development_units/resale rows with their own IDs | Traceability view is not physical deduplication and cannot be counted as unique assets |

Canonical evidence: PROJECT.md §06; migrations beginning 20260820010743 and 20260820014650; generated types `properties`, `project_units`, `property_bookings`, `property_owners`, `property_management_terms`; hooks `useProperties`, `usePropertyOwners`, `usePropertyOwnership`. Historical UNIT_TABLE_MIGRATION prose is not authority where it conflicts with these SQL/code contracts.

Buyer request metadata keeps `unit_id` as the selected project catalogue row and adds `property_id` as the canonical physical UUID, or null when unmapped. This metadata is intake context, never inventory authority. The team can distinguish missing mapping. Import staging only emits changes for known catalogue rows with an existing canonical property link and preserves that link from trusted current state; incoming file IDs cannot replace it.

Offline staging tests preserve the trusted physical/catalogue identity, reject a spoofed replacement, enforce the offer-patch field whitelist and emit no changes on repeat normalized import. This is not a lifecycle integration test: rental/PMS/ownership/building/document/history writers were not exercised. Earlier broader lifecycle claims are withdrawn; that acceptance remains outstanding.

Plan before any additive migration: inspect current IDs/constraints and orphan/alias inventory; backup; reconcile exact stable keys and project consistency; reuse current bridges; propose only missing relational FK extensions and offer/source revisions; isolated DB migration/authorization tests; separate approval/deployment. No current table is merged, deleted or repurposed by this tranche.

Physical containment must remain separate from hotel/category grouping: `useAssignRoomCategory` in `useRoomCategories.ts` clears parent_property_id when categoryId is removed. property_kind currently distinguishes unit/resort/hotel; no canonical building table was found. Therefore an apartment's physical building link must not reuse that mutable category assignment or disappear with operational regrouping. Any missing physical-containment extension must reference existing property/project UUIDs and be independently designed/tested; this tranche adds none.

The existing sync trigger only fills a NULL properties.project_id; it does not resolve a conflicting non-null project. The staging adapter requires the trusted physical property project link to equal the source project and sends mismatches to reconciliation. A newly authorized physical unit must receive its canonical properties.id when first created, never a replacement UUID on completion. No such creation was performed in this tranche. Applied migration history is preserved; this ADR supersedes conflicting legacy documentation rather than editing historical SQL.

`properties` currently combines physical and listing attributes. The approved reuse contract preserves its existing UUID; further asset/listing separation needs an explicit, non-duplicating source/deployed-schema audit and compatibility plan. Current source role descriptions alone do not prove a fully separated asset/offer model.
