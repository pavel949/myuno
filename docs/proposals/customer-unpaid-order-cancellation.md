# Customer unpaid commercial-order cancellation — unapplied contract

This branch prepares the client journey and a review candidate. **Production cancellation is not enabled.** No SQL, privileges, RLS, real orders, payments, notifications or inventory were changed. The sibling SQL is deliberately outside migration directories and grants no client execute access. `FINAL_ORDER_MUTATION_SECURITY.md` remains an unresolved security audit, not authority to apply its older candidate.

## Current source and bounded change

`useOrders.cancelOrder` previously selected a status, performed a direct UPDATE with no affected-row check, then inserted history separately and reported success. It now uses the same checked command boundary as the confirmation control. There is no direct-write/history fallback. Until reviewed server commands exist, the old cancellation path fails closed and the new control is unavailable. Existing create/provider writers are unchanged and are **not certified** by this work.

`/me/payments` waiting orders and `/orders/:id/tracking` use a shared Cancel order → confirm → server result → Cancelled flow. No delete, hide, refund or service-order adapter exists. The versioned eligibility reader passes only the order id. The command passes only order id, expected server revision and a retry UUID. It never accepts a caller-selected customer, status, payment flag or total. Unknown response versions, foreign ids, missing history receipt, timeout and missing RPC never produce success. The confirmation retains the same UUID on retry. Order and payment readers refresh after confirmed success, including the existing timeline.

The payments reader now includes the actual waiting enum states, excludes deleted/paid rows from its due bucket, retains cancelled order history and propagates errors rather than fabricating an empty account. Mixed-currency balances are not added together. Missing financial values are not treated as zero/default THB.

## Required server contract and activation blockers

The read uses INVOKER; the public command wrapper uses a narrow checked DEFINER entry point. A private, checked DEFINER writer is proposed because revoking raw customer UPDATE/history INSERT also removes an invoker's ability to commit those writes. It derives `auth.uid()` internally, enforces persisted customer ownership, locks the order, requires its unchanged server revision and waiting/unpaid state, and commits the order transition and existing history together. Its search path is pinned and all privileged tables/helpers are schema-qualified. No command is granted to clients in this proposal. Existing order→property-booking trigger/inventory semantics must participate unchanged. A history UUID is the idempotency receipt: retrying the same request returns the existing cancelled event and creates no duplicate. A request UUID belonging to another order/actor/transition fails. Replays remain behind the same linked-state and cutover refusal so a late payment cannot be hidden behind an older receipt.

The original governor dependency was removed during review; the explicit cutover refusal below prevents this candidate being mistaken for deployable authority. The activation review must enforce all of the following against complete authoritative data, with no customer-editable metadata assumptions:

- Paid/deposit-paid/processing/refund/confirmed/started-work/active-checkout or ambiguous payment state refuses cancellation. Order `paid_at`, every linked payment/manual-receipt source and fulfilment/booking state must agree. Unknown or unreadable state refuses.
- Every competing checkout/payment/fulfilment writer follows a reviewed common locking and durable-attempt protocol. A row lock cannot span a Stripe HTTP call; a durable pending attempt must exist before the external side effect. Never infer quiescence from absent intents or a missing session reference.
- Shared checkout inserts a pending intent before session creation, links `provider_ref` after it, and currently treats insertion/linkage failure as non-fatal. Property/yacht and manual/wallet/legacy paths require their own writer trace. This branch does not claim that race is resolved.
- Current customer/provider direct mutation, child/payment-intent/history policies and existing guard bypasses from the security audit must not let the actor forge the facts or cancellation receipts used by cancellation checks. Closing direct history INSERT is essential; an own-order insert policy does not establish server provenance. Trigger compatibility with the private checked writer requires separate proof.
- Property inventory release is a checked atomic consequence of the canonical transition, never a `deleted_at` UI operation. No linked `service_orders` or legacy `bookings` status is silently translated.

No helper, capability flag, grant, broad definer bypass, payment engine or second order/history table was invented to make the UI look ready. The current absent RPC produces an unavailable control. The SQL candidate must not be activated by granting execute alone.

## Acceptance gate before any separate production action

Run disposable PostgreSQL integration tests with actual applicable guards, policies and bridge triggers: foreign customer/guest/role denial; every blocked financial/fulfilment state; source read failure; zero-row/stale revision; history/trigger failure rollback; linked inventory release; duplicate/concurrent cancellation; same UUID with wrong actor/order; cancel versus checkout-intent creation/session-link/webhook/manual receipt; retries after transport uncertainty. Prove no committed charge is stranded and no inventory is released on refusal.

Client synthetic tests cover missing/malformed/denied contracts, confirmation, uncertain results, retry identity, unavailable states, locale labels and payment error/mixed-currency behavior. They are not a substitute for the unresolved checkout cutover, disposable SQL tests or production evidence. Root coordinates exact reviewed SQL and action-time access separately; no migration application is authorized in this task.

The payment reader retains paid-at order activity regardless of current valid order status, alongside completed, refunded and cancelled orders. History amounts are labelled order amounts: an unpaid cancelled order is not a charged payment. This bounded reader is not certification of the complete financial ledger. Unknown actors have no inferred currency or balance.

## PR review correction: blocked rollout and concrete checkout interlock

This is **not merge/deployment ready**. `useBooking.cancelBooking` delegates to `useOrders.cancelOrder`; its former direct mutation is therefore also disabled until the reviewed server command is deployed. Do not release the client/edge changes independently.

The old `create-checkout` selected no status, created Stripe checkout before persisting an intent, and ignored its order metadata update result. The revised edge requires `reserve_customer_order_checkout` before even customer lookup/creation. Its unapplied SQL locks the owned waiting/unpaid commercial order, derives price/currency and persists an existing-model pending payment_intent. Any existing intent requires reconciliation. Provider or link failure leaves it pending. Linking requires a returned matching intent row; no real provider calls were made here.

The cancellation candidate no longer delegates safety to a placeholder governor. It explicitly refuses payment_intents/manual_payment_requests/ledger_entries/order_items/property_bookings linkages and then refuses every remaining order with `checkout_cutover_and_historical_reconciliation_required`. The current schema cannot prove a trusted post-cutover cohort: historical Stripe sessions can have no intent, and other shared/property/yacht/manual/wallet writers still lack this common lock protocol. Wallet reference_id/reference_type must be audited as references, not an invented order_id FK. Core property rental cancellation remains blocked; service_orders and legacy bookings have no invented commercial FK joins.

The public command now has narrow definer ownership checks with a pg_catalog search path and qualified tables; it invokes the private checked writer without exposing the private schema to client roles. No grants or SQL were applied. History INSERT requires RETURNING, exactly one affected row and a persisted canonical row; a BEFORE INSERT trigger returning NULL must roll back the transition. Browser-session unresolved commands retain actor/order, original revision and UUID across close/reopen and useOrders callers, and retry the receipt before checking new eligibility. Page reload recovery is not provided; order history remains authoritative.

Required deployment order: review and test the reservation RPC with actual policies/triggers; close/audit competing writers and reconcile historical sessions; establish an authoritative eligible cohort; run PostgreSQL suppression/rollback/concurrency/inventory tests; only then review cancellation activation and coordinated edge/client rollout. This branch applies none of those production actions.

Install/create/revoke must execute as one reviewed transaction with an explicit least-privilege function owner; the candidate wraps BEGIN/COMMIT and leaves cancellation EXECUTE revoked. Deploy and verify all reservation handlers before considering cancellation. Grant the narrow cancellation entry point LAST, then release UI. UI hiding alone does not protect RPC execution. No private-schema exposure is needed.

The supplied suppressed-history SQL regression is UNEXECUTED: this executor has neither postgres nor psql on PATH. It requires a dedicated myuno_cancel_test_* database and synthetic owned pending fixture, injects a BEFORE INSERT NULL trigger, exercises the otherwise cutover-blocked body only inside a rollback transaction, and asserts no false receipt or surviving order transition. It does not establish actual-policy/inventory/race proof.
