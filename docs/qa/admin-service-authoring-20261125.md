# Service and supplier authoring: class B candidate

- Canonical scope: supplier `providers`, offering `services`, public `public_service_catalog` and `public_provider_catalog`. No change to SQL, grants, account linking, service requests, routing to suppliers, notifications, charging or settlement.
- In both existing supplier editors and service editor, ordinary create is inactive, pending and unverified. The pending state is used for a nonpublic draft, not proof of review. Existing admitted admins have a separate **Approve and publish** action for a saved unapproved record; published records can use the existing active switch. A supplier trust badge is separate and never set by a publish action. New service publication requires an active approved non-demo supplier, a returned active category, a positive recorded price and a currency code. An ordinary save never changes approval. These are UI/workflow checks over existing database policies, not new security authorization.
- Clear values use explicit `null`/empty array rather than omission. Edit and duplication keep the source currency unless edited explicitly. The authoring form no longer sends the two unsupported `max_capacity` and `is_featured` service keys. No local deletion of media files is attempted.
- Existing visible category links read all corresponding known canonical category/service slugs *before* the 60-row page window. Unverified life situations or home-request template IDs are never substituted for an offer relationship. Subsequent pages are user-driven and bounded at 60 raw rows per page (with stable sort by creation and ID). Existing Unicode text matching by English/Russian offer name and provider name applies to each page, not a falsely labelled global sort/search, and remains unchanged for local-language fallback. A missing offer on one page is not proof of absence from the catalogue.
- Synthetic local tests can verify source paths, field payloads, identity and category scoping, and client success/failure. This is not evidence of deployed view/RLS, live vendor rights, availability schedules, operator receipt parity, or actual email/WhatsApp delivery. For release, verify exact staged actor admission and the matching scoped operator request on the release environment; do not open a new public booking flow or alter supplier access.
