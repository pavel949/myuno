## Problem and resulting behavior

ServiceOrderSuccess and WellnessOrderSuccess previously ignored read errors and fell through to UnifiedSuccessLayout's unconditional “Payment confirmed” header after missing-row retries. Wellness also claimed a confirmed booking regardless of persisted status. The follow-on caller audit found MarketSuccess trusted a URL order number alone, EventSuccess promised tickets/email, TransferSuccess promised a driver, and FlowersSuccess could clear the cart after missing-row exhaustion or delete new unrelated flower cart items when revisiting a confirmed historical receipt. All six callers are included in this routine presentation tranche. An error, absent row, checkout-return URL or commercial order is not payment/capacity proof.

All six pages now show separate checking, error, missing/unverified, signed-out, pending and persisted order states. Only known persisted confirmed/in-progress/completed order statuses receive a positive order-status heading. No audited caller asserts that payment or service capacity was confirmed. Existing service request copy still requires price/time/provider confirmation. Unknown or cancelled/refunded statuses never become a positive confirmation. Missing wellness category/currency is not converted to Beauty/THB. Unverified service returns prioritize My orders over creating another request. Receipt-driven flower cart clearing is removed entirely: an owned confirmed historical order does not prove that current cart rows belong to that order. Purchased-cart reconciliation needs an explicit checkout/cart association, not this read-only return page.

The shared layout accepts an optional title/tone/retry state and now defaults to neutral unverified presentation. All six actual callers were audited. Persisted positive headings explicitly describe the order status, not payment verification, ticket issuance, email delivery, provider capacity or driver assignment. Other checkout/payment endpoints and return pages outside this layout are not certified by this tranche.

## Read contract

- Require a resolved signed-in actor; constrain every order read by `customer_user_id` and the intended vertical/order type. A URL or navigation order ID grants no authority.
- Keep the service legacy session link in order metadata. Independent review rejected an initial wellness `payment_intents.provider_ref` lookup: checkout writes `cs_*`, but the webhook later overwrites it with `pi_*`. It is not durable session identity. No backend writer was changed to conceal that gap.
- The existing `useStripeUnifiedCheckout` now retains only explicit server-returned session/order IDs as one actor-bound sessionStorage navigation hint with a 30-minute TTL. No Stripe URL parsing, payment state or order data is cached. Storage failure never changes a created checkout into a failure. Wellness treats that ID as an untrusted selector and freshly reads only the current actor's beauty/fitness/medical order. A missing, expired, wrong-actor/session or unreadable hint remains explicitly unverified with My orders access; there is no broad or transient-payment-reference fallback. Another device/session without the hint cannot resolve this historical session-only return automatically.
- Use explicit field projections and no domain cache. The narrow `useOrderReturnRead` projection extracts the already-tested read-state mechanism for all six callers. Existing `useOrderTracking` cannot safely represent this requirement: it uses wildcard private fields, an actor-free cache key, timeline RPCs and realtime subscriptions. The new hook reads the existing canonical orders/children only; it creates no order, booking, payment, service-order or financial truth. The local result is bound to actor plus checkout reference and cannot flash a prior actor's details during an account switch.
- Missing/pending rows poll at most ten times at two-second intervals. A ten-second read deadline becomes a visible error. Query errors stop polling until an explicit retry. Cleanup clears timers, aborts the in-flight read and discards late responses after unmount/account/reference changes.
- No payment intent status, paid flag, ledger entry, reservation or financial transition is inferred or written.
