# myuno: исправления после проверки готовности

Дата: 15 ноября 2026. Репозиторий: `pavel949/myuno`. Ветка: `fix/production-readiness-20261115`. Исходный коммит: `be1224b5ed838bffebffddf12b127871adf41bad`. Это **myuno**, не отдельный проект myUNO-final.

**Промышленный запуск остаётся NO-GO.** Подготовлены изменения исходного кода, проверяемые SQL-кандидаты и порядок выпуска. Производственная база, функции, роли и бизнес-записи не изменялись; платежи, возвраты и сообщения реальным пользователям не отправлялись. Ниже отделены исправления кода от эксплуатационных условий, которые ещё нужно выполнить.

## Изменения

| Найденная проблема | Подготовленное исправление |
|---|---|
| THB ошибочно считался валютой без дробной части; 950 THB превращались в 950 сатангов | THB использует два знака: 950 THB → 95000. Старые недоплаты нельзя принять через совместимость со старым множителем. |
| Клиент мог выбирать сумму внутри диапазона скидок | Сервер вычисляет единственную цену из применимых сохранённых тарифов. Конфликты тарифов требуют решения; сроки ранней/срочной скидки проверяются. |
| Заказ и удержание дат создавались отдельными запросами | Проверяемая транзакция создаёт заказ, позицию, гостя и удержание дат. Создание вручную требует администратора либо сохранённых полномочий на бронирование и финансы конкретного объекта/компании. |
| Подтверждённый заказ позволял webhook пропустить недостающую оплату/бухгалтерию | Проверенная Stripe-квитанция, заказ, inventory и ledger сверяются под блокировкой. Повторное событие восстанавливает недостающую работу; ошибка возвращает повторяемый ответ вместо ложного успеха. |
| Депозит мог выглядеть полной оплатой | Частичное поступление сохраняется отдельно, без признака полной оплаты и полной проводки заказа. Остаток остаётся долгом. |
| Ручная RUB-оплата не имела проверенного курса/документа/границы полномочий | Реализованы одобренные владельцем правила: администратор или уполномоченный вводит фактически полученные RUB, согласованный курс RUB за THB, проверяет документ и его уникальный номер. Повтор документа не создаёт второй платёж. |
| Consultation RPC создавал новый UUID при повторе | В пакет приёмки включён уже существующий кандидат `docs/hardening/consultation-intake/forward.sql` с общим клиентским helper и rollback. Рабочий RPC пока не обновлён; новая параллельная реализация не создаётся. |
| Гостевая ручная заявка создавала несколько независимых записей | Серверная цена и одна транзакция заказа/гостя/удержания/заявки; повтор после потерянного ответа использует прежний ключ и возвращает ту же заявку. |
| Форма подставляла расчётную сумму как фактически полученную | Поле фактической суммы пустое; обязательны курс, документ и ссылка на него. Загрузка документа сохраняется для неизменённого повтора после неясного ответа. |
| Экран гостя обещал подтверждённую бронь и отправленный ваучер при любом подтверждении | Частичная оплата показывает остаток THB; переплата/неясные старые платежи показывают необходимость сверки. Полное подтверждение показывается только после `settled`, доставка письма не объявляется состоявшейся заранее. |
| Уполномоченный сотрудник не мог пользоваться административной страницей | Та же форма доступна по существующей странице конкретной заявки после серверной проверки полномочий; общая административная зона не открывается. |
| Браузер мог напрямую создавать/менять финансовые записи | SQL-кандидат закрывает прямые финансовые записи заказов/позиций/платежей/ledger. Старая форма создания «оплаченного» заказа заменена переходом к проверке поступления по заявке. |
| Принятие трансфера оператором трактовалось как оплата; отклонение могло начать возврат | Операционное принятие не создаёт ledger. Непроверенная отмена/возврат блокируются до отдельного атомарного процесса. |
| Получатель денег мог приходить от клиента либо подменяться ID провайдера | Используется только однозначная защищённая связь provider → активная org. При отсутствии/неоднозначности связи финансовая операция блокируется либо направляется на сверку. |
| Анонимный и неполный экспорт мог считаться резервной копией | Только серверный ключ, точный count, все страницы, проверка первичного ключа, manifest и SHA-256. Любая ошибка запрещает успешный снимок/импорт. |
| Список экспорта устарел и предполагал `id` у каждой таблицы | Read-only инвентаризация рабочей базы: 432 public base tables, 13 ключей не `id`, включая составные. Экспорт сортирует по реальным ключам, импорт использует их как conflict target. |
| Приватные выгрузки сохранялись открытым артефактом | AES-256-GCM, только шифротекст в артефакте, удаление plaintext. Плановое задание больше не импортирует данные автоматически; импорт в зеркало только по отдельному ручному запуску. |
| Критические/высокие уязвимости зависимостей | Обновлены совместимые зависимости и необходимые major-версии MapLibre, Vitest, MCP SDK; исправлена интеграция MapLibre и matcher types Vitest. Critical/high: 18 → 0. |

Сохраняются канонические источники: коммерческий заказ — `orders`, аренда/inventory — `property_bookings`, полученные деньги — проверенные `payment_intents`, бухгалтерия — `ledger_entries`. Отдельные таблицы бронирования, валютных курсов, ledger или ролей не создавались. Метаданные остатка и статуса являются проекцией проверенных поступлений.

Одобренная ручная доплата с новым документом может закрыть точный остаток. Переплата, возврат и изменение уже согласованной стоимости требуют отдельного решения/проверяемого процесса. Подтверждение документа само не переписывает стоимость заказа. Из старых платежей не делается массовое «доверенное» заполнение.

## Проверки

Использованы синтетические провайдеры/документы, отдельные PostgreSQL 18.6 Unix-socket кластеры и запрет исходящих соединений к размещённым backend. Реальные записи рабочей базы не использовались как QA. Локальная среда: Node 24.22.1 / npm 11.9.0; репозиторный CI использует Node 22, его отдельный результат пока не подменяется локальным.

| Полный прогон с `--maxWorkers=2`, без одновременной сборки | **5064/5064 PASS**, 443 файла, 0 пропусков, 580.88 с |
| После последней защиты уникальности файла документа | **68/68 PASS**: actual PostgreSQL Stripe settlement, manual receipts и managed booking; повторены все три финансовые SQL suite |
| Backup + actual Stripe/manual receipt/manual request handlers | **19/19 PASS**; SDK, signature verification и доставка заменены синтетическими границами |
| Signed transfer operator ingress + conflicts | **19/19 + 5/5 PASS**, внешняя сеть и реальные возвраты запрещены |
| TypeScript / ESLint / production build | **PASS** последовательно на итоговом исходном коде; ESLint: 0 ошибок, 2214 предупреждений; build: 7176 modules, 2m 1s, PWA создан |
| Финальный `npm audit` | 0 critical, 0 high, 28 moderate, 2 low |

Полный прогон завершён перед последним усилением SQL-индекса уникальности proof path и защитой от отката подтверждённого поступления в статус contacted; вслед за этим все 68 финансовых PostgreSQL тестов повторены на итоговом SQL, включая новый отрицательный сценарий. Это дополнительные проверки, не 68 новых независимых сценариев сверх полного прогона. Итоговый код не проверялся реальным списанием Stripe или отправкой письма.

Предыдущий прогон одновременно со сборкой дал 13 сбоев в четырёх файлах. Отдельные повторы и затем полный прогон без этой нагрузки прошли; старый неуспешный результат не используется как положительное доказательство. Исходный прогон до расширения ручной оплаты также проходил 5022 теста. Исходные результаты аудита с отсутствующими PostgreSQL binaries не выдаются за результаты исправленного окружения.

## Что необходимо до запуска

- Зарегистрировать и выпустить новые миграции вместе с соответствующими Edge Functions и интерфейсом, сверив текущие определения/права. SQL пока остаётся review-кандидатами: CLI в этой среде не смог создать конфигурацию в read-only домашнем каталоге. История миграций не подменяется ручным именованием.
- Сверить ранее принятые платежи, недоплаты THB, частичные/неполные проводки, удержания дат и реальные связи получателей. Ничего не списывать и не возвращать автоматически.
- Настроить секреты резервирования и проверить полноценное восстановление schema/data/Auth/Storage на изолированной базе. REST-снимок public-строк не обеспечивает единую транзакционную точку во времени и не является полной аварийной копией.
- Указать реальные назначения сотрудников и объектов перед включением Operating Spaces. Read-only аудит показал ноль пространств/активных назначений/компаний с enforcement; код не создаёт вымышленные назначения.
- Проверить совместимость всех старых финансовых редакторов и отмен с закрытием прямых записей. Произвольная отмена, возврат и изменение старого заказа пока не объявляются поддержанными. Проверить приёмку resort/rate-plan и доставку уведомлений в изолированной среде.
- Разобрать оставшиеся зависимости: финальный `npm audit` — 0 critical, 0 high, 28 moderate, 2 low. Среди них Router 6, ExcelJS и build-инструменты. Это число package nodes, не число доказанных эксплуатаций. Принудительные понижения версий из `audit fix --force` не выполнялись.
- Провести representative load, проверить мониторинг ошибок и зафиксировать требуемые RPO/RTO; эти эксплуатационные свойства исходными unit-тестами не сертифицированы.
- Подтвердить соответствие точного SHA опубликованному frontend и версиям Edge/DB; совпадение исходников само этого не доказывает.

## Пакет выпуска и откат

[Контракт](../hardening/production-readiness/CONTRACT.md), [последовательность выпуска и блокеры](../hardening/production-readiness/RELEASE.md), [read-only preflight](../hardening/production-readiness/preflight.sql). У каждого нового SQL writer есть соседний `*-rollback.sql`: он останавливает запись, сохраняя доказательства платежей и ограничения безопасности. Старые широкие права не возвращаются.

Правило репозитория, [PROJECT.md §20](../../PROJECT.md#20-change-governance): «Passing tests is evidence, not automatic approval». Поэтому промышленное включение требует отдельного GO/NO-GO по конкретному проверенному пакету. Разрешение исправить код и принятые правила ручной оплаты не подменяют приёмку этого финансового выпуска.
