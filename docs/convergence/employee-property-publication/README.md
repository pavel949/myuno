# Checked employee property publication: isolated source candidate

Status: SOURCE CANDIDATE, NO-GO for production activation. Base `dec344de58a05a2b707c619d132cf8a58ba6878d`.

No live database read/write, invitation, migration, permission grant, push or deployment was performed. These transaction-wrapped files are outside both migration journals. Preparing source does not authorize applying it.

## Why the narrow author relation is necessary

- Existing `mc_member_update_company_properties_v2` uses `staff_can_access_property_e28_private`, without `properties/edit`, and permits whole-row changes. Approved active canonical rows are immediately public.
- Existing checked creation creates a canonical property and Space assignment, but does not explicitly set draft state, rejects staff, and supplies no safe creator resume relation. Setting employee `owner_id` would confer unrelated ownership rights.
- A `property_manager_assignments` row with even empty permissions enables legacy media, amenities, reviews, categories/rates, keys, utilities and payout policies. Making the base property readable also enables indirect financial/rate policies. Neither is a safe content-author relation.
- The candidate therefore adds one nullable immutable `properties.content_author_user_id` referencing `auth.users`. It is set only by checked creation, has no backfill, and is never an owner or operational manager. No new property table, revision table, base-table SELECT policy, operational assignment or automatic permission grant is introduced.
- `publish_property_to_marketplace(uuid)` remains a client-callable, unchecked SECURITY DEFINER entrypoint in source. Its current canonical view omits `amenities`, although the function reads `op.amenities` and the base `properties.amenities` column exists (`text[]`, confirmed by read-only metadata on 2026-10-19). The exact source-shape fixture expects that failure on both insert/update branches; no successful current clone/publication bypass is claimed. The candidate still revokes client EXECUTE from PUBLIC, anon and authenticated instead of relying on this incidental legacy defect. It neither repairs the publisher nor widens the canonical view.

## Main candidate contract

`checked-publication.candidate.sql`:

1. Existing `create_managed_property_checked(company, space, title_en, title_ru, property_type, listing_type)` keeps its UUID return. It explicitly creates inactive `draft`, owner/provider NULL, instant booking false and actor-bound content author. It atomically associates an active same-company Space. Every non-platform-admin creator needs active company membership, explicit active Space membership, and properties view AND edit. This requirement applies even when Space enforcement is false. Inconsistent edit-without-view is rejected before creating a shell. No manager assignment is written.
2. `list_managed_property_authoring_spaces_checked(p_company_id uuid)` returns only `{id,name_en,name_ru}` for active, explicit same-company Spaces. It requires properties view/edit and active company authority. Protected platform admins may see active same-company Spaces. This avoids treating the legacy resolver's empty Space list as authorization.
3. `read_managed_property_draft_checked(p_property_id uuid)` returns a safe JSON row. `list_managed_property_drafts_checked(p_company_id uuid,p_limit integer DEFAULT 50,p_offset integer DEFAULT 0)` returns SETOF safe JSON rows for the current creator only; limit is 1–100. Missing authority raises or filters rows, never falls back to a broader property query.
4. Safe row fields are exactly the 156 catalogue fields in `src/lib/managedPropertyDraftFields.ts`, plus `id`, `management_company_id`, `approval_status`, `is_active`, `created_at`, `updated_at`, `rejection_reason`. Owner/provider/creator IDs, owner contact, lock codes, iCal token, private financial records and review actor identities are not returned. Pending/approved rows remain safe-readable so creators can see review outcomes.
5. Author read/save rechecks active same-company membership, explicit active Space membership and current module action. The relation authorizes only its creator, unless an existing operational manager independently passes `actor_can_operate_property`. It never broadens that operational helper. Deleted properties are unavailable. Platform-admin authority is protected, not generic uno_team.
6. `save_managed_property_draft_checked(p_property_id uuid,p_expected_updated_at timestamptz,p_patch jsonb,p_submit boolean DEFAULT false)` is SECURITY DEFINER because new content authors have no raw property access. It checks actor authority before and after locking the row, requires the exact persisted version, rejects unknown fields, applies canonical database types and validates both the proposed and resultant row. It returns the same safe row as read; no base-table readback is needed or allowed as fallback.
7. Only inactive, nondeleted draft/rejected rows can be saved. Saving produces draft; submitting produces inactive pending. Pending content is frozen. Approved/active content is not employee-editable. Rejected rows retain previous review evidence while being corrected. No implicit unpublish or later revision system is implemented.
8. Changed tariff/payment fields require the proposed explicit `pricing/edit` text-keyed module in existing `team_member_permissions`; no finance authority is implied or granted. Changed booking mode, stay or availability terms require `bookings/edit`. Both require the already-proven property author scope. Unchanged values do not require extra grants. The global operational module whitelist is unchanged. The shared subsets contain 47 pricing and 17 booking fields; `seasonal_pricing` requires both. Non-default initial listing mode also needs bookings/edit; the content-only default is an inactive rent shell, instant booking disabled.
9. New complex links require an active same-company canonical complex. New project links require an active same-company or approved publicly listed canonical project. An established project link cannot be replaced in this workflow. No grouping link grants operational scope.
10. A final invoker trigger protects direct managed writers too: properties/edit, same field allowlist, pricing/bookings checks and inactive draft/rejected transitions. Managed direct INSERT is rejected for non-platform-admin sessions, avoiding self-ownership or already-approved insertion. Existing independent owner/provider UPDATE paths and unmanaged workflows remain under their prior policies. Creator identity cannot be rewritten by ordinary client updates, including platform-admin client updates.
11. The final timestamp trigger produces a strictly advancing server revision for direct AND definer writes, including repeated writes in the same transaction. Callers preserve the exact timestamp string; parsing through JavaScript Date can lose precision.
12. `review_property_submission_checked(property_id,expected_updated_at,decision,reason)` is SECURITY INVOKER and protected-platform-admin only. It locks and compares inactive pending state and exact version. Approve publishes; rejection requires a reason and stays inactive. The existing admin UI can instead retain its RLS writer with pending+updated_at compare-and-set and verified returned row. The source UI does not silently switch to an undeployed RPC.
13. The existing `property_activity_log` records actor, state change and revision token atomically through a non-client-callable trigger. A restrictive INSERT policy reserves only `managed_property_draft_created` and `managed_property_publication_changed` against direct client forgery; the old broad client INSERT policy remains valid for other legacy action names. Audit failure rolls back the transaction; no snapshot is a second property truth.
14. Submission notifications use the same persisted object gate before and after edge readback. Scoped author/edit is permitted only for inactive pending rows, alongside existing owner/admin authority. Recipient selection remains protected-admin-only. New edge with old SQL remains fail-closed. Notification failure must not erase or falsely deny a persisted pending submission.

## Explicit limits

- Project creation remains a separate unimplemented canonical contract. Complex creation is a separate source-only candidate in `../employee-complex-publication/README.md`; neither candidate is activated by property draft linkage.
- Existing operational managers retain their independent child-table authorities. The new creator relation confers none; it does not rewrite every existing operational domain.
- Reviewed media is not immutable or tamper-proof. Normal PhotosStep editing writes new vendor-uploads/property-care keys, ImageEditor writes new keys and gallery removal changes only URL references. Nevertheless existing vendor-uploads uid-prefix Storage UPDATE/DELETE policies (`20260110082249`) can mutate/delete approved URL bytes; videos have analogous property-videos policy (`20260424161200`). Remote URLs have independent mutability. This is pre-existing media-integrity hardening work, not solved here.
- Independent owner/provider/admin legacy publication rights are preserved. The candidate is not a universal owner-publication lockdown and does not relax existing Space ceilings.
- Ownership evidence, CRM/management assignment, accounting, payment recipient/identity, access secrets, moderation and badges are excluded. Unsupported meaningful input must be visibly unsupported, not silently claimed saved.
- UUID-only creation can leave a retained draft if a later save fails. Resume that ID through checked read; do not duplicate automatically.
- Source vendor moderation notification references `NEW.name_en` although canonical properties use `title_en`. Actual trigger definitions and behavior need authorized verification and production-equivalent isolated replay.
- Legacy active pending rows are outside the new review RPC. No bulk state repair is included.
