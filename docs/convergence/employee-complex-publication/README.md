# Governed employee complex authoring: source candidate

Status: **SOURCE CANDIDATE. NO-GO for production activation.** Prepared 19 October 2026 on the employee-workflow integration source. Files remain outside both migration journals. No SQL, grants, invitations, Edge functions, deploys or production business writes are authorized by this document.

## Canonical boundary and reason

`property_complexes` is the existing complex grouping catalogue. `property_projects` is a separate development/project domain. This candidate neither replaces nor conflates them. It creates no parallel complex, draft, publication, property, assignment or permission table.

The current source `MC members can manage company complexes` policy is `FOR ALL` using `get_user_company_ids()`. It permits a content-only employee to mutate active complex rows without a properties action, review or Space check. Public SELECT exposes the whole row, including ownership and juristic/CAM fields. Adding nullable author/reviewer metadata without containing those policies would create additional disclosure and publication paths.

The existing table requires `owner_id`. An employee preparing catalogue content is not thereby the legal owner. The checked workflow therefore permits NULL owner only when a complete governed author/company/Space/status contract is present. Ordinary owner records keep the existing owner relation.

## Contract

`checked-complex-publication.candidate.sql` is transaction wrapped and requires the reviewed private authority helpers, existing Operating Spaces, existing `admin_audit_logs`, and the preceding checked property-authoring Space picker.

1. Add nullable `content_author_user_id`, `authoring_space_id`, `approval_status`, `reviewed_by/at`, `approved_by/at`, and `rejection_reason`. No default, bulk backfill or reinterpretation of old active rows. Legacy rows retain NULL review status. A same-company composite Space FK and NULL-safe CHECK require a complete governed row; draft/pending/rejected are inactive and approved is active.
2. The creator and authoring Space are immutable, including through the definer/service write path. Governed company and owner are immutable too. Future ownership/reassignment or deletion needs a separately governed contract. Creation sets owner NULL and actor from `auth.uid()`; it creates no property-manager or Space-property assignment.
3. Authoring always requires an existing active company and active same-company Space. Non-platform-admin actors need active company membership, explicit active Space membership, and properties/view plus the requested action. This remains required when Space enforcement is false. Generic `uno_team`, cached context and an empty resolver scope grant nothing.
4. The creator alone, or a protected platform admin, can read/save the governed draft through checked RPCs. Author read/list returns only the 20 existing catalogue fields in `src/lib/managedComplexDraftFields.ts` plus `id`, `management_company_id`, `authoring_space_id`, `approval_status`, `is_active`, `created_at`, `updated_at`, `rejection_reason`. It omits owner/author/reviewer identities, juristic contacts and CAM/financial fields. No author base-table SELECT policy is added.
5. Atomic creation validates and persists full content plus draft or pending state in one INSERT. Validation/trigger failure leaves no orphan shell. Saves lock the row, require its exact opaque `updated_at` token, validate a strict field allowlist and canonical database types, then check the resultant row. Version timestamps advance strictly, including within one transaction; the client must never round them through JavaScript Date.
6. Only inactive draft/rejected content may be saved. Save resets to draft; submit becomes inactive pending. Pending and published content is frozen for all direct client writers, including admin clients. This candidate implements no approved-content revision/reopen or deletion path. Rejected rows retain prior review evidence during correction.
7. Admin review requires protected platform admin before and after the row lock and after the update. It compares the exact pending version, verifies active company/Space and validates content. Approval makes that exact version active; rejection requires a reason and remains inactive. It changes no catalogue content. A stale or racing decision fails rather than silently overwriting.
8. The broad MC policy is replaced by action-specific legacy read/update/delete policies. Legacy operational access must pass current properties/view and requested action, active company membership, and all linked non-deleted properties' existing `actor_can_operate_property` checks. Cross-company or partially authorized linked properties deny the entire complex. Unlinked complexes require the existing company-overseer helper. Existing operational staff/accountants/member roles are preserved only when those existing object/action checks actually pass; the candidate grants them no assignment. Independent owner and protected admin rights remain separate.
9. A non-admin cannot create a managed row with self-as-owner, or create an unmanaged owner row and then attach it to a company to bypass checked creation. Non-admin raw legacy company reassignment requires a future checked workflow; independent owner content edits remain intact.
10. `public_complex_catalog` is read-only and allowlisted. It exposes only active legacy rows (`approval_status IS NULL`) or approved active governed rows. The old raw public SELECT policy is removed; private owner/admin/verified-manager reads remain under RLS. A restrictive authenticated raw-read ceiling contains extra permissive policies without granting authors raw access. Public amenities and picker labels use the safe view. The source consumer inventory includes `usePropertyComplexes.ts` and the private name lookups in `OwnerProperties.tsx`; there are no other direct complex-table readers found in `src` or `supabase/functions` at this tranche.
11. The existing `admin_audit_logs` records actual admin review actor, complex ID, previous/result status, active flag and exact revisions atomically. It contains no full content snapshot and is not a second complex truth. Restrictive INSERT/UPDATE/DELETE policies reserve only `managed_complex_reviewed`, preventing direct client forgery or tampering even under the existing admin ALL policy. Audit failure rolls back publication. Creation provenance is immutable creator/created_at; this tranche does not claim an append-only history of every draft save/submission.

## RPC interfaces

All actor identity is derived server-side. These signatures match the employee client:

- `create_managed_complex_checked(p_company_id uuid, p_operating_space_id uuid, p_patch jsonb, p_submit boolean DEFAULT false) RETURNS jsonb`
- `read_managed_complex_draft_checked(p_complex_id uuid) RETURNS jsonb`
- `list_managed_complex_drafts_checked(p_company_id uuid, p_limit integer DEFAULT 50, p_offset integer DEFAULT 0) RETURNS SETOF jsonb`
- `save_managed_complex_draft_checked(p_complex_id uuid, p_expected_updated_at timestamptz, p_patch jsonb, p_submit boolean DEFAULT false) RETURNS jsonb`
- `list_managed_complex_submissions_checked(p_company_id uuid DEFAULT NULL, p_limit integer DEFAULT 50, p_offset integer DEFAULT 0) RETURNS SETOF jsonb`
- `review_managed_complex_submission_checked(p_complex_id uuid, p_expected_updated_at timestamptz, p_decision text, p_reason text DEFAULT NULL) RETURNS jsonb`

The first four return the same safe row. Author list is current actor only, including review outcomes. Admin queue returns inactive pending rows only. Limits are 1–100 with nonnegative offsets. Review decisions are `approve` and `reject`. UI selection reuses `list_managed_property_authoring_spaces_checked(uuid)`; each complex mutation independently verifies company active status and complete scope.

## Explicit limits and activation gate

- This is a source-only candidate, not an applied migration or live capability. Clients must fail closed when the RPC/view is unavailable; no raw-table fallback for employee content is allowed.
- The source UI deliberately keeps generic staff out of the old raw company-complex editor while production might still have the old broad MC policy. A legitimately assigned operational staff member can retain server authority to a legacy complex but may need a later checked discovery affordance to surface it in that editor. This does not create a new staff grant.
- Complex public image/video URLs retain their underlying storage/remote-URL mutability. Review does not make media bytes immutable.
- Legal ownership, juristic contact management, CAM pricing, finance, company/Space reassignment, linking properties, project authoring and published-content revisions are outside this tranche. Grouping never grants access to a linked property.
- No notification delivery or email/Edge change is included. The persisted review queue is authoritative for submission outcome.
- Legacy independent-owner/admin publication rights remain separate. Tightening the managed authoring path is not a universal owner-publication redesign.

## Fail-closed rollback

`docs/hardening/rollback/employee_complex_publication.candidate.sql` revokes authenticated EXECUTE for the six checked workflow RPCs. It preserves all canonical rows, author/scope/review evidence, audit data, restrictive write/read/audit guards and safe public projection. It never restores membership-only complex writes, raw public rows, a fabricated owner, or prior broad grants. The UI should report unavailable checked authoring rather than invent a fallback.
