01

Principles

The rules every structural decision defers to.
Principle 01

One person, many roles

Role is not an onboarding choice. It's a stack the user edits over time. The home blends signals across roles; no role-switching modals.

Principle 02

Cluster over catalog

45 apps live in 6 colour-locked clusters. Users learn spatial meaning (Legal is always amber) so new apps don't create new mental load.

Principle 03

Concierge is an agent, not a bot

The AI layer isn't a chat window — it's a silent router that schedules, drafts, and confirms. Users see intents, not prompts.

Principle 04

Surfaces, not screens

Home, Wallet, Me, Discover, Operate, Admin are surfaces — long-lived canvases the cluster modules mount into. No route explosion.

Principle 05

Events over direct calls

Every state change fires a typed event. UI, notifications, and AI all subscribe. One bus replaces the cross-import spaghetti.

Principle 06

Trust is UI, not a footer

License, audit trail, and regulatory markers live on every money-moving screen — not on a /legal page nobody visits.

02

The role model

Six roles, multi-select, weighted. One primary. The foundation for everything that ranks.

A role isn't a persona — it's a current-state claim. "I'm a Resident" means today I'm paying rent and renewing a visa. Tomorrow I may also be Owner (my villa is rented out) and next week a Tourist (visiting friends in Krabi). The role stack is always editable from the home.

Navigation shell

One shell, two variants (mobile / desktop). Tabs stay stable; role changes never move them.

Mobile · 4 tabs

Home · Discover · Wallet · Me. Operate appears only when the user has a professional role (Owner, Agent, Developer, Provider) — replacing Discover for those sessions, not adding a 5th tab. The tab count never exceeds 4.

Why not a 5th tab

Mobile hit-target math: a 402px phone with comfortable spacing accommodates 4 tabs at 44px each with 8px gutters. A 5th tab either shrinks targets below accessibility floor or forces a "More" drawer — which is where apps go to die. Operate takes Discover's slot because the two audiences rarely overlap in a session (nobody shops for a spa appointment while reviewing their pipeline).

Hard rule

L5 cluster modules may only depend on L4 domain primitives & L3 services. They never import from other L5 clusters. This is how the 45-app problem stops being 45×45 = 2,025 possible interactions and becomes 45×6 = 270.

09

AI agents & event bus

How the concierge is wired without becoming a chat blob.

Every L4 domain primitive emits typed events (booking.confirmed, visa.expiring, payment.failed). Three things subscribe:

UI
Home feed · Surfaces
Events render as activity rows, signal cards, and badge counts. UI never polls — it reacts.
Notifications
Push · email · SMS
A single router reads the event, applies user preferences, and fans out. No per-vertical notification code.
AI agents
Scheduler · Drafter · Advisor
Subscribe to events, produce intents — "offer to schedule extension", "propose uplift rate" — that surface in the home concierge card. Never chat. Always one-tap yes/later.

Canonical data model

The nouns. Everything in the app is a view over these.
Person // one row per human ├─ roles: [tourist, resident, owner, ...] ├─ primary_role ├─ kyc_level ├─ consents[] ├─ documents[] → Document ├─ persons_of[] → Company └─ memberships[] → Household Company // legal entity — agent firm, developer, provider, MC ├─ company_type: agent | developer | provider | mc ├─ members[] → Person └─ properties[] → Property Property // single unit OR development ├─ owner → Person | Company ├─ managed_by → Company (MC) ├─ listings[] → Listing ├─ bookings[] → Booking └─ documents[] → Document Listing // offer — stay, service, product, property-for-sale ├─ cluster · vertical ├─ provider → Person | Company └─ items[] → item-type-specific Booking · Order · Contract · Ticket // all inherit: id, actor, counterparty, state, payments[], messages[], events[] Payment // money movement, attached to any domain object Document // pdf/image + signed events Message // threaded, attached to any domain object
Row-level security

Every table carries person_id and/or company_id. Supabase RLS policies read the session role stack and enforce: a person sees their own rows + rows of companies they belong to + public listings. No bespoke per-vertical auth logic.

Cleanup plan

What to collapse to get from the current state to this blueprint.

  • 11+ shell layouts (AppLayout, MiniAppLayout, mc/*, portals, landings)

  • Single notification router subscribed to the event bus
12

Migration roadmap

Six phases, each independently shippable. No long freeze.
Phase 1 · Role stack
~ 1 sprint
Add roles[] + primary_role to Person. Migrate single-persona users. Ship role sheet on Home. Zero new features — just the data model.
Phase 2 · Surface consolidation
~ 2 sprints
Collapse shells. Reroute /mc, /owner-portal, /developer-portal, /vendor under /operate/*. Preserve old URLs via redirects for 90 days.
Phase 3 · Cluster routing
~ 2 sprints
Every vertical moves to /app/:cluster/:vertical. Standard template. Discover landing pages become /discover/life/:situation.
Phase 4 · Event bus + agent registry
~ 2 sprints
Typed events from L4. Agent registry in L3. /admin/agents observability. Migrate existing AI calls to intents.
Phase 5 · Design tokens single source
~ 1 sprint
Deprecate tokens.json. ESLint rule to block hardcoded colours. Update DS docs so every component example compiles.
Phase 6 · Trust & compliance pass
~ 1 sprint
Inline licence + audit-trail markers on every money-moving screen. Consent ledger unified. PDPA & SEC evidence surfaces in /me/consents.
Shipping order rationale

Role stack first because every downstream phase assumes it exists. Surfaces before routes so UI collapse happens before URL churn. Agents after routes so the event taxonomy is stable. Tokens & trust last — they're polish, and touching them mid-restructure creates merge hell.
